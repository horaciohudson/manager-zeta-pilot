# ZetaPilotAI Manager — Architecture Decision Records

Each decision records its context, decision, alternatives, and consequences. Pending decisions are listed at the end.

---

## ADR-001 — Credit-based usage instead of a fixed subscription

- **Context:** The original plan proposed a fixed subscription (~$10/month) for BYOK starting in 2027. Cline, the product's foundation, is free and open source. A license checked only by the client is a "system of honor" when users provide their own keys, because there is no server-side resource to protect.
- **Decision:** Remove the standalone fixed-subscription phase. Sell pay-as-you-go credits consumed by AI requests routed through the Manager gateway. A future subscription may exist only if it includes a credit allowance.
- **Alternatives:** (a) A fixed BYOK subscription was rejected because it competes with free Cline. (b) Keeping three phases (fixed fee, then tokens) was rejected because it delays the correct model and creates unused schema and expectations.
- **Consequences:** The Manager needs a critical AI gateway and credit ledger, provider working capital, anti-abuse controls, and LGPD responsibilities for prompt traffic.

## ADR-002 — BYOK alongside the managed provider

- **Context:** Credit-based usage could otherwise remove support for users' own provider keys.
- **Decision:** Keep two paths: free BYOK requests go directly from the extension to the provider; paid ZetaPilotAI requests go through the managed gateway. Both appear in the extension's provider list.
- **Consequences:** BYOK has no provider cost for us and supports user acquisition; the gateway is the paid path. BYOK keys stay in extension SecretStorage, while master keys stay on the server in secrets.

## ADR-003 — Spring Boot, React, and PostgreSQL on our own VPS

- **Context:** The original document called the stack mandatory without explaining why.
- **Decision:** Use Java 17/Spring Boot 3, React/TypeScript/Vite, PostgreSQL, and Docker/Nginx on the existing VPS. Follow the established geo-limites conventions: the same versions (Spring Boot 3.3.3, JJWT 0.12.3, springdoc 2.5.0), layered packages, Flyway migrations, database-configurable SMTP, and one Dockerfile per component. This improves consistency and maintainability across projects.
- **Alternatives:** Supabase and Firebase were rejected because Phase 2 requires control over AI gateway streaming, metering, and the financial ledger, as well as data hosted on our own infrastructure.
- **Consequences:** More initial work than a managed platform, in exchange for consistency with team experience, VPS isolation, and no commercial-phase rewrite.

## ADR-004 — Devices are telemetry during the free phase

- **Context:** The original plan limited and revoked devices during the free phase.
- **Decision:** Record devices as telemetry visible to users and administrators, with no enforcement. Revisit limits only if justified by a future commercial model.
- **Consequences:** Less user friction and support work, less enforcement code, and a simpler `Device` entity.

## ADR-005 — Move extension integration earlier as a vertical slice

- **Context:** The original plan put extension integration near the end, despite it being the critical path and highest-risk area.
- **Decision:** Build the vertical slice (sign-in → activation → license validation in the extension) immediately after users, devices, and licenses, before completing the admin dashboard.
- **Consequences:** Technical risk is addressed early. The full admin dashboard can follow without blocking the extension launch.

## ADR-006 — Welcome credits only at commercial launch

- **Context:** Giving away credits during the free phase would add provider costs before the commercial model is ready.
- **Decision:** Issue welcome credits only when Phase 2 launches; include the existing free-user base as a conversion incentive.
- **Consequences:** No provider spending during Phase 1; the credit grant becomes part of the commercial launch plan.

## ADR-007 — Stable device UUID generated by the extension

- **Context:** The Manager must identify extension installations without relying on unstable device fingerprints.
- **Decision:** Generate a UUID on the extension's first run and store it in VS Code SecretStorage. Send it with activation and license-validation requests.
- **Consequences:** Stable identification without collecting hardware fingerprints; reinstalling after SecretStorage is cleared creates a new device record.

## ADR-008 — Extension sign-in through a browser and `vscode://` callback

- **Context:** The original contract suggested entering a password into the extension using `POST /api/auth/login`.
- **Decision:** Follow the VS Code flow: the extension opens a browser, the user signs in to the frontend, the frontend redirects to `vscode://...?code=...`, and the extension exchanges the one-time code for tokens. The extension never handles the password.
- **Consequences:** A familiar and more secure user experience, requiring a one-time-code endpoint and an extension URI handler.

## ADR-009 — Accept a single-VPS single point of failure

- **Context:** The Manager will initially run on the company's existing VPS.
- **Decision:** Accept a single point of failure in Phase 1, mitigated by the extension's seven-day grace period. Revisit in Phase 2 when the gateway becomes critical to AI requests.
- **Consequences:** Lower cost and complexity now; risk is contained by the extension design.

## ADR-010 — Prepare only commercial architecture seams

- **Context:** "Prepare the architecture for billing" is ambiguous and may create unused schema.
- **Decision:** In Phase 1, prepare only `LicensePlan`, `License.status`, empty `gateway` and `credit` module boundaries, and the managed-provider concept in the extension. Do **not** create payment, AI gateway, or ledger tables before Phase 2.
- **Consequences:** No dead schema; Phase 2 starts from a foundation rather than unused infrastructure.

## ADR-011 — Transactional email through panel-configurable SMTP

- **Context:** Registration and account recovery require transactional email. The team already operates a configurable SMTP implementation in geo-limites.
- **Decision:** Store administrator-configurable SMTP settings in the database, adapting the `SmtpSettings`/`SmtpMailService` design to the Manager domain. Encrypt the SMTP password at rest with an environment-provided secret, never return it from the API, and provide connection and delivery tests.
- **Consequences:** P1 is resolved. SMTP management and email delivery are Phase 1 work; each environment's administrator supplies the actual credentials.

## ADR-012 — Keep tokens out of JavaScript-accessible browser storage

- **Context:** The web dashboard and VS Code extension are distinct environments; `localStorage` is not appropriate for authentication tokens.
- **Decision:** Do not persist tokens or credentials in `localStorage` or `sessionStorage`. The web dashboard uses `HttpOnly`, `Secure` (over HTTPS), and `SameSite` cookies with appropriate CSRF protection. The extension uses the one-time-code flow through `vscode://` and stores tokens only in VS Code SecretStorage.
- **Consequences:** The backend must support cookies for the web client and bearer tokens for the extension, configure cookie attributes per environment, and implement one-time-code exchange. The extension remains a separate project and is not implemented in this repository.
